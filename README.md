# Store Intelligence

Store Intelligence is a retail analytics project that turns CCTV-derived person movement into store operations insights. It includes a FastAPI backend, SQLite persistence, a mocked-testable video analytics pipeline, and a Streamlit dashboard.

The repository is submission-ready as a compact challenge implementation: it favors clear service boundaries, deterministic tests, local-first setup, and documented assumptions over production infrastructure.

## Project Overview

The system accepts business events such as `ENTRY`, `ZONE_ENTER`, `ZONE_DWELL`, `BILLING_QUEUE_JOIN`, and `EXIT`. Events can be posted directly to the API or generated by the video pipeline. The API stores events, rebuilds visitor sessions, and exposes metrics, funnel, queue, anomaly, and heatmap analytics.

Typical flow:

1. Start the FastAPI server.
2. Run the video pipeline against one video or a directory of camera videos.
3. Pipeline writes `detections.jsonl` and `events.jsonl`.
4. Pipeline uploads generated events to `POST /events/ingest`.
5. Rebuild sessions with `POST /sessions/rebuild`.
6. Query APIs or open the Streamlit dashboard.

## Features Implemented

- Batch event ingestion with per-event validation.
- Idempotent deduplication by `event_id`.
- SQLite persistence through SQLAlchemy ORM.
- Store metrics: unique visitors, entries, exits, staff entries, dwell, peak hour, queue joins, queue abandons, abandonment rate, and conversion rate.
- Visitor session rebuild from historical events.
- Funnel analytics for entered, engaged, queued, and converted visitors.
- Queue status classification: `NORMAL`, `BUSY`, `CONGESTED`.
- Anomaly detection for long dwell, queue congestion, traffic spike, low conversion, and empty store periods.
- Zone heatmap analytics with visit count, unique visitors, average dwell, and normalized heat score.
- OpenCV + YOLO detection pipeline.
- Centroid-based tracking and per-run visitor IDs.
- Multi-camera directory processing with per-camera output folders and aggregate store summary.
- Pipeline event generation and upload to the ingestion API.
- Streamlit dashboard for API-driven operational views, including distinct camera count.
- Dockerfile and Docker Compose for local API deployment.
- Test coverage for API routes, services, pipeline components, and mocked end-to-end flow.

## Running the Video Pipeline

### Single-Camera Mode

Place a real video under `data/`, for example:

```text
data/store.mp4
```

Start the API, then run:

```bash
python pipeline/run_pipeline.py --video data/store.mp4 --store-id STORE_001 --camera-id CAM_1
```

The pipeline:

1. Opens the video with OpenCV.
2. Runs YOLO person detection.
3. Writes person detections to `data/pipeline_outputs/detections.jsonl`.
4. Tracks people across frames.
5. Resolves tracked people into configured zones.
6. Writes business events to `data/pipeline_outputs/events.jsonl`.
7. Uploads events to `POST /events/ingest`.

### Multi-Camera Mode

Place camera videos in one directory:

```text
data/videos/
|-- cam1.mp4
|-- cam2.mp4
`-- cam3.mp4
```

Run:

```bash
python pipeline/run_pipeline.py --video-dir data/videos --store-id STORE_001
```

Supported extensions are `.mp4`, `.avi`, and `.mov`. Files are processed independently, so one camera failure does not stop the remaining cameras.

Camera IDs are inferred from filenames:

```text
cam1.mp4        -> CAM_1
cam2.mp4        -> CAM_2
store_cam5.mp4  -> CAM_5
front_door.mov  -> CAM_1 if it is first in sorted order
```

Generated visitor IDs are camera-scoped in multi-camera mode, for example `CAM_1_VISITOR_000001` and `CAM_2_VISITOR_000001`. This prevents analytics from merging unrelated visitors detected by different cameras.

Multi-camera output structure:

```text
data/pipeline_outputs/
|-- CAM_1/
|   |-- detections.jsonl
|   `-- events.jsonl
|-- CAM_2/
|   |-- detections.jsonl
|   `-- events.jsonl
`-- CAM_3/
    |-- detections.jsonl
    `-- events.jsonl
```

At completion, the command prints a store-level JSON summary:

```json
{
  "store_id": "STORE_001",
  "cameras_processed": 3,
  "cameras_failed": 0,
  "total_tracks": 12,
  "total_visitors": 12,
  "total_events": 48,
  "uploaded": 48,
  "failed": 0,
  "camera_summaries": []
}
```

After upload, rebuild sessions:

```bash
curl -X POST "http://127.0.0.1:8000/sessions/rebuild" \
  -H "Content-Type: application/json" \
  -d '{"store_id": "STORE_001"}'
```

## Zone Configuration Guide

Zones are configured in `pipeline/zones.json`. Each zone is a rectangle with `x1`, `y1`, `x2`, and `y2` coordinates in video pixel space.

Important zones:

- `ENTRY_ZONE`: when a tracked person enters this zone, the pipeline emits `ENTRY`.
- `BILLING_ZONE`: entering this zone emits `BILLING_QUEUE_JOIN`.
- `EXIT_ZONE`: entering this zone emits `EXIT`; leaving billing through this zone is treated as successful checkout and does not emit `BILLING_QUEUE_ABANDON`.

Example zone:

```json
{
  "zone_id": "ENTRY_ZONE",
  "x1": 0,
  "y1": 0,
  "x2": 220,
  "y2": 220
}
```

The zone coordinates must match the camera layout and video resolution. In multi-camera mode, the same `pipeline/zones.json` is applied to each camera video, so videos should use compatible layouts or the zone file should be adjusted before processing. If the coordinates do not overlap the actual person positions in the video, the detector may still find people but zone-based events may not be emitted. In that case the pipeline summary can show:

```text
Events generated: 0
```

When using a new video, inspect representative frames and update `pipeline/zones.json` so entry, billing, product, and exit areas cover the correct pixel regions.

## Assumptions & Limitations

- SQLite is used for local persistence and challenge simplicity.
- No authentication or authorization is implemented.
- No database migrations are included.
- Visitor IDs generated by multi-camera mode are camera-scoped, for example `CAM_1_VISITOR_000001`; they are not reconciled as the same physical person across multiple cameras.
- Session analytics depend on running `POST /sessions/rebuild` after ingesting historical events.
- Zone analytics depend on correct `pipeline/zones.json` coordinates for the input video or videos.
- YOLO model download/runtime requirements depend on the local environment.
- The dashboard is an operational view over API responses, not a separate production frontend.
